# Security

The studio is a single-owner app. It holds unpublished scripts, voiceovers, videos, book files and the owner's notes and ratings. The goal is that only the owner (in the browser) and the worker (through a narrow API) can read or change anything, and that nothing the worker reads can steer it into leaking or destroying data.

## Threat model

| Who / what | What they could try | Main controls |
|---|---|---|
| Anyone on the internet | read or write studio data with the public anon key | RLS on every table and the bucket (owner only, via `studio_owner`); sign-ups disabled; `0003_hardening.sql` removes all `anon` grants and `write_doc` execute from `anon` |
| A signed-in non-owner | same, with a valid session | RLS checks `studio_owner` membership, not just "signed in"; the UI shows "not the studio owner" |
| Someone who finds `/api/fire` | burn routine runs, learn the config | owner JWT checked first (401/403 before any `not_configured`); 60 s rate limit claimed with a versioned write, failing closed (429/503) |
| Someone who finds `/api/worker` | read or change data | `WORKER_TOKEN` bearer (≥ 32 chars, constant-time compare); 1 MB JSON-only POST; per-table write rules; no delete action |
| Prompt injection in what the worker reads (book text, web pages, screenshots, chat messages) | make the worker overwrite, delete, exfiltrate or post | playbooks treat all content as data; the API itself enforces: no deletes, no ratings, no owner fields (`captionFinal`, `posted`, `dropReason`), existing packs/ideas only take specific merges, history and metrics append-only, jobs only for the claimed run, the only creatable job is a server-shaped auto-art job; uploads only under `media/ frames/ exports/`, downloads only under `books/ media/ frames/ stats/ exports/` |
| A leaked browser bundle | find secrets | only the public anon/publishable key is bundled; the build refuses any other key; a test scans the repo for keys |
| XSS | run script in the owner's session | React escaping, no `innerHTML` with data; CSP `script-src 'self'` plus the hash of the one inline theme script; `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`; https-only links with `rel="noopener noreferrer"` |
| Files | public links to private media | private `studio` bucket; documents store paths; the browser gets 1-hour signed URLs, the worker 10-minute ones |

## Controls in code

- `api/_lib/worker-core.ts`: auth order, table and field rules (`writeRule`), auto-art rule, weekly jobs, path regexes. Unit tested in `test/unit/worker.test.ts`.
- `api/_lib/fire-core.ts`: owner check before config, `claimFireSlot` (versioned, fails closed). Tested in `test/unit/data.test.ts`.
- `vercel.json` headers, generated by `scripts/csp.mjs`; a test checks the inline-script hash.
- `scripts/anon-key.mjs`: the build only accepts `sb_publishable_…` or a JWT with `role: "anon"`.
- `.github/workflows/pages.yml`: `contents: read` at the top; `pages: write` and `id-token: write` only on the deploy job. The demo build is checked for any Supabase or `/api` reference.
- Dependencies are pinned to exact versions; Vercel and CI install with `--ignore-scripts`.

## Residual risks and follow-ups

- **Worker network egress.** The API limits what the worker can change, not what it can read and send elsewhere. Keep the routine's environment on Trusted (or a narrower Custom list), never Full. With full internet access, an injected instruction could make it send studio data out.
- **Web fetch tools.** Even with a network allowlist, the worker's own web search/fetch tools can reach the web (scout and trends need them). Treat anything the worker can read as potentially disclosable through those tools, and keep the most sensitive material (for example unreleased book files you don't own) out of the studio.
- **WORKER_TOKEN is a long-lived bearer.** Anyone with it has the worker's (limited) powers. It is stored as an API credential on the routine's cloud environment, so the worker session never sees it and an injected instruction can't print or send it. Rotate it on any suspicion and periodically.
- **No lockfile yet.** The npm registry was not reachable from the build environment, so `package-lock.json` has not been generated. Exact version pins limit drift, but transitive dependencies are not locked. Follow-up: run `npm install --package-lock-only` on a machine with registry access and commit the lockfile, then switch CI to `npm ci --ignore-scripts`.
- **The service role key** lives in Vercel only; a Vercel account compromise exposes everything. Use 2FA on Vercel, GitHub and Supabase.
- **Rate limit granularity.** `/api/fire` allows one fire a minute; a stolen owner session could still fire once a minute until the session is revoked (Supabase > Auth > Users > sign out user).

## Rotating tokens

- **WORKER_TOKEN:** generate a new one (`openssl rand -hex 32`), set it in Vercel and redeploy, then delete and re-add the routine environment's API credential with the new value. Calls with the old token get 401 straight away.
- **ROUTINE_FIRE_TOKEN:** regenerate the routine's API trigger token, update `ROUTINE_FIRE_URL`/`ROUTINE_FIRE_TOKEN` in Vercel and redeploy.
- **SUPABASE_SERVICE_ROLE_KEY:** rotate in Supabase (API keys / JWT secret), update Vercel, redeploy. Rotating the JWT secret also signs out every session and invalidates a legacy anon key, so update `SUPABASE_ANON_KEY` and rebuild too.
- **Owner session:** Supabase > Auth > Users > the owner > sign out of all sessions.
